# Jensen Grid Verification Release — E2 (v1, repaired 2026-11-24)

A computational supplement to "Certified Log-Concavity of the
Riemann–Jacobi Kernel and a Source Audit of a Pólya-Type
Real-Zero Criterion" (kernel paper concept DOI
10.5281/zenodo.20465035). This release packages the program's E2
certification of Jensen polynomials for the Riemann–Jacobi kernel
Φ: the data, the operative script, and the method records, so the
certification can be inspected and replayed without the program's
internal files. File hashes and sizes for everything in this
package: see `INVENTORY.md` in this package.

Positioning (program record, POSITIONING.md): the kernel paper is
a classical-analysis and verification contribution. This release
is a verification release, not a paper claim, and nothing in it is
progress toward the Riemann Hypothesis. A finite grid, certified
or not, proves nothing beyond the grid.

## The claim, stated exactly

Let H(z) = ∫₀^∞ Φ(u)cosh(u√z)du = Σ a_k z^k = Σ γ_k z^k/k!, so
γ_k = k!·a_k. Two families of Jensen polynomials are certified,
and they are always cited separately:

- **Standard ξ family:** J^{d,n}(x) = Σ C(d,k) γ_{n+k} x^k.
- **Borel family:** J^{d,n}(x) = Σ C(d,k) a_{n+k} x^k — the Jensen
  polynomials of B(z) = Σ a_k z^k/k!, the Borel transform of H.

The two results, each independently attributable:

- **Standard ξ family: CERTIFIED 231/231** on the grid
  d = 2..12, n = 0..20 — every J^{d,n} hyperbolic (d distinct
  real roots) — with 0 failed and 0 indeterminate, against
  interval enclosures of the true coefficients. Certificate:
  `results_adj3.json` (sha256
  981078c5f7f25177b9791f717e97af4772d7babbc770ce866aa5cd7a1d399769)
  — the **aggregate certificate-of-record payload**: per family
  it stores a tally and the (empty) set of non-certified
  exceptions, not per-polynomial records; the grid it refers
  to is attributed by its generating procedure and the method
  records, not by a grid ledger inside the file (see
  `SCHEMA-CROSSWALK.md` in this package).
  Worst discriminant relative width in that certificate:
  2.61e-11, at J^{12,20}.
- **Borel family: CERTIFIED 231/231** on the same grid
  d = 2..12, n = 0..20, with 0 failed and 0 indeterminate,
  against interval enclosures of the true coefficients.
  Certificate: `results_adj3.json` (same payload; the two
  families' aggregate tallies are recorded separately in it).

Both certifications are Sturm certification in FLINT/Arb ball
arithmetic from the widened moment balls W_k below.

## Why the balls are widened (the repair this release embodies)

The first certification runs enclosed only the six-term
truncation's moments I_k. A Co-scientist round-3 audit proved the
omitted n ≥ 7 summation tail fatal to containment at three
indices: the omitted contributions, enclosed in Arb at 512 bits,
are δa_0 = 2.148808e-65, δa_1 = 2.259718e-70,
δa_2 = 2.316534e-75, each exceeding its accepted ball's diameter,
so the true a_0, a_1, a_2 lay outside the accepted balls.
Scope correction (round 4, adopted verbatim): "Position-
independent noncontainment is proved for k=0,1,2. This test does
not establish containment in the old balls for the remaining
moments. After widening, containment is established for all
k=0,…,32."

The repair widens every ball by a proved tail bound,
W_k = I_k + [0, D_k] (D_0 = 2.184234e-65). The derivation is
reproduced in full in `DK-DERIVATION.md` in this package; the
script header of `e2cert3.py` carries the same derivation in
compressed form. (The round-3 adjudication, §1.5, is the
historical record of the derivation's independent verification;
it is background, and is not required for replay or for
verifying the bound.) The repair re-runs only the
polynomial-level Sturm certificates — no new integrations. The
root counts never changed: the original counts were correct for
the coefficients actually enclosed, and the widened re-runs
return identical counts for the true kernel's coefficients.

A note on reading the certificate: its `ball` string fields
are the authoritative enclosure representation. The numeric
`mid`, `sup`, `lower`, and `upper` fields beside them are
binary64 diagnostic renderings of the balls' midpoints and
endpoints and are **not** outward bounds (a rendering of an
endpoint can fall on either side of the true endpoint).
`SCHEMA-CROSSWALK.md` gives the full schema map and the safe
endpoint-extraction procedure; `CERTIFICATE-ENDPOINTS.json`
carries the exact decimal endpoints of every ball in the
certificate (all 68 balls: r*, the 33 D_k, the 33 failure-set
deltas, and W_0), computed from the printed strings.

## Supersession

`results_e2cert.json`, `results_e2cert2.json`, and
`results_e2gamma.json` are **superseded as true-kernel

## Replay

### Environment

Reference environment (the environment of record, read back from
the venue): **Python 3.12.3** with **python-flint 0.9.0**, which
bundles **FLINT 3.6.0** (Arb is part of FLINT 3), on Linux x86_64
(glibc 2.39). The historical host is tower-compute and its TC-03
venv; that is provenance, not a requirement. A supported replay
environment is any Linux x86_64 host with Python 3.12 and
python-flint 0.9.0:

```
python3 -m venv venv
venv/bin/pip install python-flint==0.9.0
```

`e2cert3.py` imports only `flint` beyond the Python standard
library. Every certification setting is fixed in the script
itself (there is no configuration file): the precision ladder
256/512/1024/2048 bits, integration tolerances
rel = 2^-(prec−64) and abs = rel·1e-12 with eval_limit 10^7 and
depth_limit 1000 in the `acb_integral` calls, KMAX = 32, and the
two grids. Because the settings live in the hashed script, the
inventory hash on `e2cert3.py` pins them.

### Setup

The script reads two cross-check files at startup, at the fixed
paths `~/riemann-runs/e2-20261122T143947/results_e2.json` and
`~/riemann-runs/e1-20261122/moments_partial.json`. Stage the
packaged copies there (hashes in `INVENTORY.md`):

```
mkdir -p ~/riemann-runs/e2-20261122T143947 ~/riemann-runs/e1-20261122
cp crosscheck-inputs/results_e2.json ~/riemann-runs/e2-20261122T143947/
cp crosscheck-inputs/moments_partial.json ~/riemann-runs/e1-20261122/
```

Run the script from a writable scratch copy of the package: it
writes its payload into its own directory, and a full run there
would overwrite the recorded `results_e2cert3.json`.

**Run-output lifecycle (follow exactly).** The script never
deletes anything, and its payloads carry no timestamp or
invocation identifier, so a payload left over from an earlier
run is indistinguishable from a fresh one. Before every run,
delete the four output names from the scratch copy:

```
rm -f results_e2cert3.json results_e2cert3_smoke.json \
      results_e2cert3_selftest.json results_e2cert3_ERROR.json
```

The recorded payloads remain untouched in the package of record,
where the comparison contract below reads them. Under this
lifecycle, any payload present in the scratch copy after a run
was produced by that run; see "Exit status and verdicts" for
what a failed run leaves behind.

### Exit status and verdicts

The process exits **0** whenever a run completes and writes its
payload — whatever the tallies. The verdict is in the payload,
never in the exit code: read `results_by_family.<family>.tallies`
and, for a full run, `label_outcome`. If the 77-point control
block does not certify in full, the full run's `label_outcome`
says so ("NO VERDICT: …") and the batch is NO VERDICT. A
polynomial proved NOT hyperbolic is recorded as "failed" in the
tallies and named in `label_outcome` (a certified
non-hyperbolicity outcome for that family and polynomial). The
process exits **1** only on an unhandled exception; it then
writes `results_e2cert3_ERROR.json` and produces no new verdict
payload. It does **not** delete or overwrite anything else:
verdict payloads already in the directory (the recorded payloads
packaged with this release, or outputs of earlier runs in the
same scratch copy) survive a failed run untouched, and must not
be read as the failed run's result. Under the Setup lifecycle
(outputs deleted before the run), an exit-1 run leaves the ERROR
file and no verdict payload. If you did not delete first,
attribute by timestamp: a payload older than the run, or older
than `results_e2cert3_ERROR.json`, is not the latest
invocation's output.

### Comparison contract (against `results_adj3.json`)

A replay's agreement with the certificate of record has two
separate parts, and they must not be conflated: the
**certification outcome**, which is what makes the replay a
reproduction of the certificate, and the **reference-run
regression checks**, which record the recorded run's expected
numerical behavior. Failing a regression check is a reportable
finding; it is not, by itself, a failed certification.

**Certification outcome — a replay reproduces the certificate
when all of these hold** (schema paths for every field named
here are in `SCHEMA-CROSSWALK.md`; the certificate and the
replay payload have different schemas, and the crosswalk, not
this summary, is the operative specification):

- **Direct comparisons against the certificate match exactly:**
  per family (payload keys `gamma` and `borel`), the tally at
  the certificate's `widened_reruns.<family>.tally` against the
  replay's `results_by_family.<family>.tallies` (certified /
  failed / indeterminate counts; the replay's tally adds a
  `total` field the certificate does not carry), and the
  certificate's non-certified set (empty) against the set of
  non-certified records in the replay. Agreement here is
  agreement with the certificate's aggregate all-certified
  result.
- **Replay-only assertions hold in the replay payload itself**
  (these fields exist only there; the certificate contains
  none of them): the coverage check passes — for each family,
  `results_by_family.<family>.polynomials` holds every
  intended (d, n) pair, d = 2..12, n = 0..20, exactly once —
  every polynomial's individual `status`, the full run's
  `label_outcome`, `control_block_all_certified` true, and
  both moment cross-check flags true.
- **On the reference environment, these match as strings:** the
  D_k ball strings for all k = 0,…,32 and the W_0 ball string
  (both are recorded in `results_adj3.json` and in the replay
  payload). In a different environment the trailing digits may
  differ; enclosure validity is the binding requirement, and any
  difference is reportable, not silently acceptable.

**Reference-run regression checks — expected, and reportable
when they deviate:**

- `seconds_total`; the precision level at which a given
  polynomial is decided; and the discriminant ball strings and
  relative widths may all differ across runs and environments.
  Against the recorded replay, two benchmarks are expected: the
  worst discriminant relative width does not exceed the
  certificate's 2.612920159759354e-11, and the worst polynomial
  is the standard ξ family's J^{12,20} (the recorded replay's
  worst is 1.495401392981139e-11 at that polynomial;
  FULL-GRID-REPLAY.md explains why the replay's enclosure is
  the tighter one).
- Exceeding the width benchmark, or a different polynomial
  attaining the worst width, does **not** by itself invalidate
  the finite-grid certification: a valid enclosing computation
  can produce wider balls while still proving every required
  result, and a tighter computation can move the maximum-width
  polynomial elsewhere. Report the deviation; the certification
  stands or falls on the certification outcome above.

Byte identity of a JSON payload is **not** required and is not
the replay contract.

A replay that disagrees on the certification outcome is a
finding, not a nuisance — report it against the hashes in
`INVENTORY.md`.

## Scope of this release

These certificates establish only the separately reported
finite-grid results for the standard ξ and Borel families. They
establish no result outside the stated grid and constitute no
progress toward the Riemann Hypothesis.
